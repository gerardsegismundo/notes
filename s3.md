## 1. Amazon S3 Basics & Core Concepts

Amazon Simple Storage Service (Amazon S3) is an object storage service offering industry-leading scalability, data availability, security, and performance. 

### Core Architecture
* **Objects (Files):** The fundamental entities stored in S3. Every object consists of:
  * **Key:** The absolute path/name of the object (e.g., `media/images/photo.png`).
  * **Value:** The actual data payload (sequence of bytes).
  * **Version ID:** Unique identifier used when versioning is enabled.
  * **Metadata:** Key-value pairs containing object properties (system-defined like `Content-Type`, or user-defined).
  * **Tags:** Up to 10 key-value pairs per object for access control and billing tracking.
  * **Access Control Lists (ACLs):** Individual object-level permissions (largely legacy; IAM/Bucket policies are preferred).
* **Buckets (Containers):** Objects are stored in buckets. 
  * Buckets must have a **globally unique name** across all AWS accounts.
  * Buckets are defined at the **Regional level**, but the S3 namespace is global.

### S3 Basics Cheat Sheet
* **Object Size Limits:** Max object size is **5 TB**. Max payload size for a single upload operation via `PutObject` is **5 GB**. For objects larger than 100 MB, **Multipart Upload** should be used; it is *required* for objects larger than 5 GB.
* **Consistency Model:** Amazon S3 delivers **strong read-after-write consistency** for PUT and DELETE operations of objects in all AWS Regions. This applies to both writes of new objects and updates to existing objects.

### S3 Standard Storage Class
* **Durability:** **11 9s (99.999999999%)** design durability by replicating objects across a minimum of 3 distinct Availability Zones (AZs) within a region.
* **Availability:** **99.99%** design availability.

## 2. Advanced S3 Features

To architect cost-effective, performant, and resilient applications, you must master advanced S3 features.

### S3 Storage Classes & Lifecycle Management
Optimizing storage tiering directly influences cost-efficiency.

| Storage Class | Designed Availability | Minimum Storage Duration | Retrieval Fees | Ideal Use Case |
| :--- | :--- | :--- | :--- | :--- |
| **S3 Standard** | 99.99% | None | None | Active, frequently accessed data. |
| **S3 Standard-IA** | 99.9% | 30 days | Per GB retrieved | Infrequently accessed data needed immediately when requested. |
| **S3 One Zone-IA** | 99.5% | 30 days | Per GB retrieved | Non-critical, reproducible data stored in a single AZ (lower cost). |
| **S3 Glacier Instant Retrieval** | 99.9% | 90 days | Per GB retrieved | Archival data requiring millisecond retrieval times. |
| **S3 Glacier Flexible Retrieval** | 99.9.9% | 90 days | Per GB retrieved | Archive data with retrieval options from 1–5 mins (Expedited), 3–5 hrs (Standard), or 5–12 hrs (Bulk). |
| **S3 Glacier Deep Archive** | 99.9% | 180 days | Per GB retrieved | Long-term digital preservation with 12-hour (Standard) or 48-hour (Bulk) retrievals. |
| **S3 Intelligent-Tiering** | 99.9% | None | None | Data with unknown or changing access patterns. Automates tiering across Frequent, Infrequent, Archive Instant, Archive, and Deep Archive access tiers without operational overhead. |

* **S3 Lifecycle Rules:** Used to automate transitions between classes (`Transition actions`) or permanent deletion (`Expiration actions`).
  * Can target current object versions or noncurrent object versions.
  * Useful for compliance or optimizing logs.

### S3 Versioning & Object Locks
* **Versioning:** Keeps multiple variants of an object in the same bucket.
  * Enabled at the bucket level. Once enabled, it can only be **Suspended**, not completely disabled.
  * Deleting an object with versioning enabled creates a **Delete Marker**. To permanently delete an object, you must specify the exact `Version ID`.
* **S3 Object Lock:** Adheres to the **WORM (Write Once, Read Many)** model. Requires versioning to be enabled first.
  * **Retention Period:** Blocks deletion for a specified time.
    * *Compliance Mode:* The retention period cannot be shortened, and the protection cannot be bypassed by any user (including the root account).
    * *Governance Mode:* Special permissions (`s3:BypassGovernanceRetention`) allow authorized roles to bypass or alter settings.
  * **Legal Hold:** Places an indefinite hold on an object until explicitly removed. No retention dates apply.

### Replication (CRR and SRR)
Replication requires **Versioning** enabled on both the Source and Destination buckets.
* **Cross-Region Replication (CRR):** Replicates objects across buckets in different AWS Regions. Used for geo-redundancy, lower latency requirements, or compliance.
* **Same-Region Replication (SRR):** Replicates objects across buckets in the same Region. Used for log aggregation, or isolating production and test environments.
* *Note:* S3 can replicate objects across different AWS accounts. Existing objects are *not* automatically replicated by default when replication rules are first turned on (requires S3 Batch Operations).

### S3 Performance Optimization
* **Multipart Upload:** Breaks files into smaller chunks. Uploads occur in parallel, maximizing throughput and enabling recovery from network errors mid-upload.
* **S3 Transfer Acceleration:** Leverages AWS Edge Locations. Traffic traverses Amazon's optimized global backbone network instead of the public internet to reach the target bucket.
* **S3 Select & Amazon Athena:** * **S3 Select:** Filters data using simple SQL expressions at the storage layer, returning only a subset of data (e.g., rows/columns from a CSV or JSON file), saving network transfer and computing overhead.
  * **Amazon Athena:** A serverless query service used to analyze large volumes of unstructured/structured data directly in S3 via standard SQL.

## 3. Amazon S3 Security & Compliance

Securing data on S3 is a critical component of the SAA-C03 exam. You must understand how to enforce least privilege access control and encrypt data at rest and in transit.

### Data at Rest Encryption
S3 provides four primary models for encrypting objects at rest:

1. **SSE-S3 (Server-Side Encryption with Amazon S3-Managed Keys):**
   * S3 automatically manages keys. 
   * Uses AES-256 encryption.
   * Default encryption for all new S3 buckets.
2. **SSE-KMS (Server-Side Encryption with AWS KMS Keys):**
   * Uses AWS Key Management Service to manage encryption keys.
   * Provides audit trails via AWS CloudTrail showing exactly when a key was used to decrypt an object.
   * Subject to KMS API concurrency limits (can require performance tuning/throttling mitigation via KMS key quotas).
3. **SSE-C (Server-Side Encryption with Customer-Provided Keys):**
   * The customer manages the keys entirely; AWS handles encryption and decryption during transactions but does *not* store the key.
   * Customer must provide the encryption key in the HTTPS request header for every read/write.
4. **CSE (Client-Side Encryption):**
   * Data is encrypted locally before being transmitted over the network to S3.

### Data in Transit Encryption
* Enforced via **Bucket Policies** by explicitly denying requests that do not use secure transport protocol (`aws:SecureTransport: false`). This guarantees that connections only occur over HTTPS (TLS).

### Access Control & Permissions
* **IAM Policies:** Attached directly to users, groups, or roles to dictate what API calls they can execute against S3 resources.
* **Bucket Policies:** Resource-based policies attached directly to the S3 bucket.
  * *Common Use Cases:* Granting public read access (for static websites), enforcing cross-account access, or requiring encryption headers (`s3:x-amz-server-side-encryption`).
* **S3 Block Public Access:** A centralized bucket-level or account-level toggle that overrides any bucket policies or ACLs that allow public access. Essential safeguard against accidental data exposure.

### Network Isolation & Architecture Security
* **VPC Endpoints (Gateway Endpoint for S3):** Allows EC2 instances inside a private subnet to securely communicate with S3 without traversing the public internet or utilizing a NAT Gateway.
  * Completely free of charge.
  * Configured via VPC Route Tables.
* **S3 Access Points:** Named network endpoints attached to buckets to simplify managing data access at scale for shared datasets. Each access point has its own specific IAM policy.

## 4. Architectural Patterns & Exam Scenarios

### Scenario 1: Cost-Effective High-Volume Analytics
* **Problem:** A data analytics engine processes petabytes of raw logs stored in S3. Access patterns change dynamically; logs older than 90 days are rarely accessed but must be retrievable within minutes if audited.
* **Solution:** 1. Store active raw inputs in **S3 Standard**.
  2. Implement an **S3 Lifecycle Policy** to transition objects to **S3 Intelligent-Tiering** if the processing duration varies unexpectedly.
  3. Configure a transition rule to shift logs older than 90 days into **S3 Glacier Flexible Retrieval** with a fallback to Expedited retrieval if an urgent audit occurs.
  4. Use **S3 Select** within analytics code to extract specific data arrays, lowering processing and compute footprint.

### Scenario 2: Regulatory Data Compliance (Anti-Ransomware)
* **Problem:** A financial enterprise requires that financial records uploaded to S3 cannot be deleted, overwritten, or modified by anyone—including system administrators and security officers—for a mandatory period of 7 years.
* **Solution:**
  1. Enable **S3 Versioning** on the bucket.
  2. Activate **S3 Object Lock**.
  3. Apply a retention configuration in **Compliance Mode** set to 7 years. This locks down the data structurally, neutralizing inside threat actors and external ransomware risk.

### Scenario 3: Secure Multi-Tenant Data Aggregation
* **Problem:** A centralized SaaS platform aggregates telemetry from dozens of distinct corporate clients into a unified S3 bucket. Each client must have exclusive access to their own data folder prefix and must not view other tenant spaces.
* **Solution:**
  1. Build a **Bucket Policy** utilizing dynamic policy variables (e.g., matching the IAM role metadata or using explicit client tags).
  2. Implement **S3 Access Points** unique to each corporate client, configuring custom, tightly scoped IAM access control structures onto each distinct endpoint.
  3. Enforce **S3 Block Public Access** globally across the account.
